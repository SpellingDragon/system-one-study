# 规划自审清单（阶段 5 用）

对已产出的多级变更规划执行审查。两类检查：**覆盖性**（第一节，最重要——防执行期返工）+ 一致性（原六节）。发现缺陷按 A/B 分类，当场修复后复验。

## 一、覆盖性检查（执行期返工的解药，P1 实证五案所生）

### 5.1 目标-任务覆盖矩阵
把变更级目标（proposal What Changes、上级手册验收项、用户口头关键要求）逐关键词列表，每个关键词指认承载它的孙任务：
- "计算主体用 X 重写" → 必须存在"X 接入生产代码"的孙任务，不能只有"X 写完+对拍"（P1 漏案：内核与模型两套平行实现，对拍全绿而生产前向从不走内核）
- "跨 N 端" → 每端都有任务（或显式裁剪记录）
- 无承载者 → 补工作项或改目标措辞，二者必居其一，不许留白

### 5.2 消费者场景枚举
对每个核心产出物（内核/服务/数据格式/工具），枚举全部消费者并逐场景确认覆盖：
| 产出物 | 推理 | 训练 | 评测 | 部署/服务 |
典型漏案：内核只枚举了推理消费者——训练要 backward（整个"反向算子"工作项缺失），直到用户一句"没有反向传播需要补"才暴露。凡产出物被训练消费，追问"反向怎么办"。第二漏案（P2 实证）：**数据注册口按评测消费者设计，漏枚举训练装配消费者**——registry 只有 test 分割，执行期训练域才发现训测同集=假分风险。数据类产出物的枚举必须含 train/test 隔离断言场景。

### 5.3 配置/档位全覆盖
grep 配置文件声明的所有档位/profile（tiny/main/gate08b/...），逐一确认有对应**实跑**孙任务：
- "配置文件存在 + diff 白名单" ≠ 实跑（P1 漏案：mps_main/gate08b 配置齐而实跑缺位）
- 正式档实跑任务须含：真跑一段 + 吞吐/显存入 run + README 命令指引供择机全量

### 5.4 性能主张必须挂基准
grep 计划里的"加速/更快/低延迟"类主张——每条必须有吞吐对比孙任务与数据落 run 的验证方式。无基准的主张删掉措辞或补任务（P1 漏案："TileLang 加速"全程无基准，执行期实测才发现热态 0.5× 的负优化真相）。双树跑不了同一基准时用同树对照（R25）。

### 5.5 真实路径验证单列
grep 计划里的 mock/monkeypatch/离线兜底——凡被 mock 覆盖的路径（远端下载、外部服务、真实权重），确认另有【真实路径验证】孙任务且标注"mock 不算完成"（P1 漏案：corpus 远端下载 monkeypatch 通过，真实路径直到执行期才首验）。

### 5.6 业界对标（涉及外部技术选型时必做）
计划中的关键技术选型（模型架构/训练方法/长文策略/多模态路线）必须有当期业界调研背书（WebSearch 实查，非仅工作区参考仓）：
- 每项选型列：业界先进工作 → 架构要点 → 采纳什么/不采纳什么（参照矩阵入 design，正反例皆收——反面经验同样有价值）
- 选型与业界相悖时必须给出理由（成本/范围/教学目标），否则改选型
（P2 实证：原计划方向侥幸全对，但 backbone 候选过时、OPD 缺精确数学、长文未划"不自研"边界——全部因无调研而悬空，用户三问追问才补齐）

### 5.9 新增 capability 前的既有能力重叠检索（2026-10-08 某异构单仓项目 W1 实证回写）
计划新增任何 capability（specs/&lt;name&gt;/）前，MUST 先检索既有主 specs 是否已有同域/同义能力：
- 检索法：能力名关键词 + 同义词 grep 主 specs 目录 Purpose/Requirement 标题（例：拟立"…-request-events"类能力前，应先检该域名词族 request/event/trigger/hint/suggest）；
- 命中同域能力时三选一显式裁决：扩展它（MODIFIED delta）/明确不重合的理由入 design /放弃新增；禁止未检索即立 ADDED——否则新建能力与既有能力并行运转，正是"防熵增"要拦的形态；
- 对既有能力的真实形态（推式/拉式、字面量、缝）以 spec+代码双核对为准，勿凭记忆断言"既有只是 X，本变更补 Y"（实证：既有容量路早已是推式，而新计划误判为"只有拉式"另立推式能力，W1 执行期才发现重复）。

### 5.7 零容忍质量门的清偿归属（多代理并发时必查）
项目自有零容忍门（注释棘轮/文档新鲜度/命名门等基线为 0 的门）在多代理并发下必然被新代码触发。规划期必须声明清偿归属，否则执行期互相推诿或编排者一人清偿全场：
- 每个域代理的派发令含"自清白名单内 finding"条款（门的具体运行命令 + 自面清零判据随令下发）；
- 共享文件/全局面的 finding 归编排者或指定文档代理；
- 编排者终跑门是唯一终态判据（agent 各自绿 ≠ 整体绿）；
- 迁 prose 入注释槽前先读懂门的词法规则（多行 bullet 判 prose、变更残留词表、尾部垃圾行——详见 apply §十词法坑）。

### 5.8 多阶段 change 账目（单 change 承载多阶段时必查）
评审→探索→实施等多阶段共用一个 change 时，规划期必须声明账目规则，否则执行期会出现改写历史报告的冲突：
- 前段产物是后段的**假设输入而非结论真源**；后段对前段结论有推翻权；
- 历史（前段）文件不可变，推翻结论记录在后段汇总文件（双方证据均保留）；
- 各阶段 F 任务分号（F1–F4 / F5–F8），互不覆盖；
- 后段规划不得沿用前段被推翻的判据（需逐条列"已废判据"清单）。

## 二、依赖三方一致性

对每个二级子变更，核对三处依赖表述互相印证：
```
① proposal 头行"父变更：…（依赖 X）"
② 一级 tasks.md 编排图的边 + 清单行括注
③ 孙任务正文中实际引用的他域产物
```
- ①缺、③有 → 隐藏依赖：孙任务就地加前置标注
- ③用到的产物属"接口常数"而非实现 → 标注"开发可并行，集成需其合并"
- 同波次两域存在任何孙任务级产物引用 → 按隐藏依赖处理
- 同仓多代理并发：并发准入依据为依赖传递闭包不相交（R21，各栈探测命令实测），import/依赖表直觉不可作凭据；异构仓各语言闭包分别验收；孙任务级并发改按**触碰集**判定（改写文件 ∪ 构建闭包 ∪ 验证读取包），相交则合单或串行（R28）

## 三、A 类：结构缺陷（必须修）

- [ ] 启动门：多 change 并存时后置 change 有显式启动门（前置归档或关键域入 main）
- [ ] 波次语义：一级 tasks 头部有"波次仅为汇报分组，解锁以依赖入 main 为准"澄清句
- [ ] 一级纯编排：一级 tasks 无实现级 `- [ ]`；每子变更项附 `changes/<name>/` 路径
- [ ] 四件套完整：每个 `changes/*/` 的 proposal/design/tasks/specs 齐备
- [ ] 契约守护闭环：关键契约目录有 spec 条款 + 合并规则硬拦 + 收尾 F1 diff 断言三层

## 四、B 类：粒度与健壮性

- [ ] 偏大孙任务扫描：任何"实现+对拍+组装"或"循环+机制"二合一/三合一 → 拆分
- [ ] 验证可判定：exit 0 型或"run-id+指标存在"型；训练类不以 stdout 文本为凭
- [ ] 时间断言：CI 中的时长断言改"退出码为判定，时长为参考"
- [ ] 基准测量纪律：凡基准必有预热（编译/首访开销须排除），冷启动数据不得进决策表；双树不可编译时用同树对照（R25）
- [ ] CI 新鲜克隆等价：门禁依赖的一切必须只来自 git 面——本机在盘而仓库无有的东西每一样都是潜伏红灯（实证三连：runner 缺 torch、探测 False 连坐、语料不在仓库）
- [ ] 全局态断言扫描：测试对已导入模块/环境/进程级缓存做"不存在"断言 = 顺序依赖隐患，规划期即要求改快照差集（执行期全量套件才会引爆）
- [ ] 门控验收三态：需真实外部资源的用例，规划期即写明"无门 Skip / 有门缺凭据 Fatal / 非空转证明"三态与预算上限（R24）

## 五、编排效率推演

- [ ] **编排文档已产出且为金字塔式**：一级 change 根有 `ORCHESTRATION.md`，四层不倒装——结论层在前（抵达 DoD 的路径 + 当前最大风险各一句），其后才是分组/明细/台账（R27）
- [ ] **编排四问齐备且可执行**：**次序**（就绪队列下沉到孙任务：前置/状态/触碰集/派发单号均可填，闭包不相交有**实测凭据**而非包名直觉）· **授权**（每单白名单精确到文件且只含本单所需、共享面归属明确、偏离分级预授权/上报）· **凭据**（四查落点按单核 + 每条判据复跑命令 + 必亲验数字清单）· **释放**（每把锁**必携等待表**并写明释放后补派哪几笔 ready 单）
- [ ] **派发粒度已定**：默认域级还是孙任务级已声明；采用孙任务级时逐单写了合单判据与**拆单的解锁收益**（单均 <2 条即须论证，防 agent 数量爆炸与上下文重复加载）；跨域合单逐处证明两域白名单与触碰集均不相交（R28）
- [ ] **三处编排表述各有边界不互抄**：`specs/orchestration/spec.md`（可验收契约）↔ `design.md`（静态决策 D2/D4）↔ `ORCHESTRATION.md`（驱动方式 + 波次台账）；逐段重复即收口
- [ ] 关键路径识别：工期粗估最长链与编排图红标一致
- [ ] 风险前置：最大技术未知数（探针）在首波首孙任务，失败有回退且不阻主线
- [ ] 参照系/慢资源：对照物与慢资源缓存与开发解耦并前置
- [ ] 无环无冗余：编排图边集无环；A→B 且 A→C→B 时 A→B 可为虚线

## 六、验收闭环

- [ ] 每个 spec 场景（`#### Scenario` 恰 4 个 #）可映射到具体测试或命令
- [ ] 变更级 DoD 为可勾选清单且每条有判定方式
- [ ] 负结果条款：消融/实验类域有"零增益/发散也如实入库"契约
- [ ] 归档前置：F 任务顺序"契约断言→门禁→DoD→archive"，DoD 未过不得归档

## 七、修复纪律

1. 发现即修（文档级修复 <5 分钟，交付带病规划的代价远高）
2. 修复后复跑：openspec status 双 4/4 + 计数统计
3. 交付报告列"已修复发现"（A/B 分类），残余不修项附理由
4. 覆盖性缺陷（第一节）修复后，在被补的孙任务上标注来源（如"【P1 教训回写】"），供后续读者理解任务为何存在
5. 回写 skill 反模式前先 grep 既有编号与外部引用锚（change 文档引用 R 编号作锚），新条目接续最大编号、禁重排
