# OpenSpec 多级变更规划（multi-level spec-driven planning）

将大型实现工作固化为三级结构：**一级变更司编排、二级子变更司领域、三级孙任务司执行**；规划审"覆盖"、执行审"一致"、验收审"证据"。本 skill 源自多轮真实规划的完整复盘（含执行期返工教训），坑均已踩过并化为规则。

## 何时使用

- 用户要求"制定变更计划并拆分任务/子领域/孙任务"
- 大特性、双阶段（如学习版+正式版）、课程教师参考答案等需要多 agent/多人并行的实现规划
- 要求"多级 specs 目录结构"、openspec 层级化、编排波次
- 执行/验收既有计划（apply 编排、双路评审）

## 核心结构（三级）

```
openspec/changes/<top-change>/            # 一级：CLI 可跟踪（4/4 artifacts）
├── proposal.md                           # Why/What/Capabilities 总览（注明 spec 已下沉）
├── design.md                             # 静态决策：D2 子域表/D4 合并规则/D5 三级验收
├── tasks.md                              # 只编排：mermaid 图 + 子变更清单 + 收尾 F 任务
├── ORCHESTRATION.md                      # ★ 编排文档：计划完成的强制产物（金字塔式，派发唯一依据）
├── specs/orchestration/spec.md           # 一级仅留编排契约（启动门/波次/契约守护/DoD）
└── changes/<NN-domain>/                  # 二级：CLI 不跟踪，一级 checkbox 跟踪
    ├── proposal.md                       # 含"边界与依赖"节（关键！）
    ├── design.md                         # 技术要点/文件清单/风险与回退
    ├── tasks.md                          # 三级孙任务
    └── specs/<capability>/spec.md        # 该域验收契约
```

要点：
- spec 下沉到二级；一级 `specs/` 只放 orchestration（否则 CLI 状态不完整）。
- 二级嵌套不被 CLI 识别是**有意设计**：二级可整体提升为顶层 change 而结构无损；进度靠一级 checkbox 人工更新。

## 工作流（六阶段）

### 阶段 1 澄清范围（AskUserQuestion，2–3 问封顶）

必问三项：**裁剪面**（砍/留/最小占位）、**规模档**（环境约束下的档位）、**规范遵守度**（项目自有质量门）。

### 阶段 2 一级变更（每阶段一个 change）

`openspec new change <name>` → 依次产出 proposal / design / specs / tasks（`openspec instructions <id> --change <name> --json` 取模板）。

design.md 必含决策（编号 D1..Dn，含被否方案）：
- **D2 子域表**：`# | 子域 | spec 能力 | 一句话边界 | 外部依赖`——"外部依赖"列即接口登记表
- **D3 波次表** + 澄清句：波次仅为汇报分组，解锁=依赖入 main
- **D4 合并规则** / **D5 三级验收**（孙任务 exit 0 / 子域 scenarios / 变更级 DoD 可勾选）

### 阶段 3 二级子变更（每域四件套）

proposal 必含**"边界与依赖"**节四要素：依赖（注明接口常数 vs 实现依赖）、被依赖方、接口面、禁止事项。

孙任务三要素：`- [ ] <编号> 动词开头产出 + 关键约束 —— 验证：<可复跑命令>`；训练类验证 = run-id+指标存在。

**verify 方案三要素（规划期随任务行定死，执行期只对账不改验收面；R29）**：①**正锚**＝点名测试＋可复跑命令，测试名与 `-run` 正则逐字符一致（漂移＝零匹配空转而 exit 0）；②**负锚**＝具名负向测试（"错误路径走不通"），正式公共入口/真实路径必有，写进任务行验证面作勾选硬门；③**消费者锚**＝正式入口/真实路径调用证据（组件测试绿≠消费者成立，测试手工补接线≠生产消费者）。能机械拦的写进机器门（测试存在性/全覆盖/对齐），不能机械化的显式列出交评审；验收面被追认缩水＝该叶重开。

### 阶段 4 编排落文档（一级 tasks.md + ORCHESTRATION.md）

**tasks.md（账目）**：mermaid 跟踪图（关键路径红标）+ 头部三行（只编排 / 启动门 / 波次语义澄清）+ 清单行含孙任务级前置。

**ORCHESTRATION.md（编排文档，计划完成的强制产物，派发唯一依据）**：按**金字塔原则**写——结论先行、归类分组（MECE）、逻辑排序，四层**不得倒装**：

1. **结论层**：抵达 DoD 的唯一路径 + 当前最大风险/瓶颈，一句话（读者据此判断是否需要下钻）。
2. **分组层·编排四问**：**次序**（就绪队列到孙任务粒度：前置/状态/触碰集/单号 / 关键路径 / 本轮做不了什么）· **授权**（每单白名单精确到文件 / 共享面归属 / 预授权与必须上报的边界）· **凭据**（五查落点按单核 / 每条判据的复跑命令 / 必须亲自复验的数字清单）· **释放**（资源锁 ↔ 等待表 / 释放即补派 ready 单 / 熔断线与分段记账）。
3. **明细层**：派发单-孙任务矩阵（含触碰集与状态）、合单判据、预算上限、档位与真实路径欠账。
4. **台账层**：每轮/每单推进记录（①–⑥ 步结果 + 凭据摘要 + 计划回写项）；无凭据摘要不得写"完成"。

模板与用法见 [apply-orchestration.md](apply-orchestration.md) §〇。**三者边界**（各自职责，不互抄）：`specs/orchestration/spec.md` = 可验收的编排契约（条款/场景）；`design.md` = 静态决策（D2 子域表/D4 合并规则）；`ORCHESTRATION.md` = 怎么驱动 + 当场账。额外文件不破坏 openspec CLI 判定（实测：change 根含杂件仍报 4/4 complete）。

### 阶段 5 规划自审（最关键的防线）

执行 [review-checklist.md](review-checklist.md)。除结构一致性外，**六项覆盖性检查**（目标-任务矩阵、消费者枚举、档位覆盖、性能主张、真实路径、verify 方案可判定性）是执行期返工的解药——P1 实证：结构全绿的计划仍可漏掉“内核接入生产模型”“反向传播”“正式档实跑”三个整工作项，全部到执行期才由用户追问暴露。

### 阶段 6 执行编排（apply：多 agent 并发实施 + 验收评审）

完整 SOP 与编排文档模板见 [apply-orchestration.md](apply-orchestration.md)。

**总纲（结论先行）**：编排者对**终态**负责，agent 对**本单（白名单内的孙任务）**负责——一切"完成"以**复跑凭据**为准，不以汇报为准。三条纪律是总纲的三个切面，按 **次序 → 授权 → 凭据** 排序（详版 R6–R28）：

1. **次序**：**派发原子 = 就绪孙任务集合**，域只作边界与账目单位（R28）；并发准入 = 依赖传递闭包不相交（R21，各栈探测命令实测），不凭包名/import 直觉——到孙任务粒度即**触碰集不相交**，同文件簇必须合单或串行；共享面默认编排者单写，可按 R22 把契约冻结为签名级常数后独立派发。
2. **授权**：派发前置 = 并发资源划拨审计 + 本单边界声明（九要素）；每单写入白名单精确到文件且只含本单孙任务所需，账目单点归属（R17）。
3. **凭据**：凡报必验、凡修必回归——完成度五查（勾选真实性/产物盘点/数字溯源/遗漏检测/**生产消费者实测**）**按派发单核**＋ agent 写后校验三连是凭据可信的地基；**波次执行完、任务勾选/结束前，派独立验证子代理评估偏差**（对照原任务行验收面，非追认缩水后；R30）——产物/正式入口链路/负向锚/勾选/目标覆盖五面核查，偏差分级处置（达标勾选/补差重开/回归重验/计划回写），返工止于波内；未完成者归因后修计划再重派，执行期暴露的计划缺口必须回写计划与 skill。

**连续推进（R31）**：波次收尾完成即派发下一波，不向用户逐波请示——节奏断点只有五个法定停点（资源门缺凭据/提交归档需明示/重大取向裁定/blocked/DoD）；到停点必须停并列清单等裁定，不到停点不得停。

**纪律的载体是编排文档**（阶段 4 产物）而非会话记忆：每次派发前重读并对齐，单完/波后回填台账；凡"下一波再说"的悬置若非真裁决点，即为流程债（R18/R19/R27/R28）。

## 核心原则（源真实项目实证）

| 原则 | 一句话 | 反面教训 |
|---|---|---|
| **连续推进至法定停点** | 波次收尾（R30/勾选/台账）是记账不是停点；单完即派下一单、波完即续下一波，不等逐波指令。只在法定停点停：①资源门缺凭据 ②提交/推送/归档需明示 ③重大取向待用户裁定 ④blocked/就绪面空 ⑤DoD 达成 | 逐波待令把节奏决定权误置于每波，用户须反复下令，11 轮无谓断档（实证） |
| 风险前置 | 最不确定的探针放 W0 首孙任务，失败有回退且不阻主线 | 方言可用性未知却排在后段 |
| 参照系先行 | 双基线/对照物与开发解耦，W0 即产出 | 无参照则一切增益不可判 |
| 慢资源缓存先行 | 重型推理的离线缓存列为 W0 核心工作项 | 各消费方重复付慢推理成本 |
| 契约三层守护 | spec 条款 + 合并规则硬拦 + 收尾 diff 断言 | 仅口头约定必被顺手改掉 |
| 负结果入库 | 消融零增益/发散也是交付物，run 不删、notes 必有结论行 | 只留绿曲线 = 掩盖坑 |
| 粒度判据＋拆分下限 | 单文件单机制单测试；"一个会话可完成 + 一条验证命令"；**一级拆不出 ≥3 个文件零相交的可并发任务则合并为单**——碎单无并发收益，徒增派发开销 | 三合一大任务无法独立验证；碎单满地无并发收益 |
| **目标必有任务承载** | 变更目标的每个关键词（如"计算主体 TileLang 化"）都映射得到孙任务 | 计划审了任务一致性却漏了目标覆盖，内核与模型成两套平行实现 |
| **消费者先于实现** | 每个产出物先枚举消费者（推理/训练/评测/服务）再定验收 | 只想着推理用内核，训练要不要反向传播无人问 |
| **调度单位随就绪面下沉** | 派发原子是就绪孙任务集合；域是权限/验收单位而非调度单位；拆单收益需写进编排文档（固定开销换解锁） | 整域成单时少数 ready 项被卡住项拖住，释放事件无可消费的最小单元 |
| **verify 方案先于实现** | 验收锚（正锚/负锚/消费者锚）随任务行前置定死，完成时只对账；波后验证子代理当场评偏差 | 验收面后置→追认缩水、测试补线冒充消费者，偏差到中期复审才暴露（31 叶重开实证） |

## 反模式（均真实出现并被修复；R6–R30 详版见 [apply-orchestration.md](apply-orchestration.md)——R27 见 §〇、R28 见 §十、R29–R30 见 §十一、R6–R26 见 §八/§九；R31 详版在本 skill 阶段 6。本表为一行式索引）

规划期（R1–R5）：
- **R1 跨变更启动门缺失**：后置 change 依赖的"契约"其实现在前者 W1。→ orchestration spec 加启动门。
- **R2 波次内隐藏依赖**：同波两域有孙任务级产物引用。→ 孙任务就地标注前置。
- **R3 波次栅栏心智**：W 标签暗示整波等待。→ 头部澄清"解锁=依赖入 main"。
- **R4 偏大孙任务**：三合一。→ 拆为实现/对拍/组装。
- **R5 时间断言脆弱**：CI 断言时长被慢机误报。→ 退出码为唯一判定。

执行期（R6–R9、R15–R31，详见 apply-orchestration.md；R31 详版见本 skill 阶段 6）：
- **R6 空返即重做**：agent 空返 ≠ 未完成，先验工作区，重派令改"复跑验证"。
- **R7 信汇报不复验**：数字/绿灯必须编排者 grep 校账 + 全量复跑。
- **R8 跨域缺陷无人认领**：编排者是唯一越域裁决与修复点（修必附回归用例）。
- **R9 集成只在最后**：每轮间即做集成验证。
- **R15 编辑工具假成功**：写返回成功而文件实为占位/0 字节/晚到覆盖。→ 写后校验三连（wc+compile+锚 grep）。
- **R16 全局态脆断言**："X 不在模块表/环境为空"顺序依赖，单域绿全量红。→ 快照差集。
- **R17 并发共享资源互踩**：并发 pip、同设备双跑、账目共写、后台被信号停起。→ 派发前资源划拨审计+账目单点归属。
- **R18 锁解无人候**：资源释放（长跑完/窗口空）无人消费等待面，延后验项闲置到用户提醒。→ 锁必携等待表；释放=触发，当场消费。
- **R19 编排者假绿**：补丁脚本静默失败后外层 && 链照走 commit，“完成”声明先于落盘验证（对自身复犯 R7 两次）。→ 修复类动作 commit 前必贴三验输出（grep -c/bash -n/exit 码）；无输出=未完成。
- **R20 计费窗口付离线税**：编译类验证不需设备却在云窗口临场做，传输/工装吃掉窗口过半（三轮实证）。→ 先判定是否需设备运行时；仅编译→本地交叉工具链；上卡动作制品化 bundle。
- **R21 同仓依赖闭包污染**：多代理共改一仓，污染按**构建系统传递依赖闭包**传导而非包名直觉（编译型最重，解释型亦存在）。**热点文件（如主循环）承载多类工作时必须合单，不得按工作类型拆两单互踩。**→ 波次依据=闭包不相交（各栈探测命令实测）；代理窗口内保持本包可编译/可导入；红绿采证用 overlay/备份复原法。详见 apply §九。
- **R22 共享面可独立派发**：默认"编排者单写共享面"非唯一路线；先把跨包接线契约冻结为签名级启动常数，再按闭包拆分把共享面分派并发代理。详见 apply §九。
- **R23 骨架错位归因**：验收测试失败先三分——产品缺陷/骨架与既定契约语义错位/环境噪声；错位则修骨架断言而非改产品。详见 apply §九。
- **R24 门控验收三态**：无门=合法 Skip；有门缺凭据=Fatal；非空转证明=用不可路由端点证明真发起过调用且零产出拒收。详见 apply §九。
- **R25 同树对照基准**：before 树编不了新 bench（新 API 不存在）时，同树新旧 API 并存同 fixture 对照，差值即新增开销。详见 apply §九。
- **R26 index 污染**：仓内工具的 intent-to-add 会把代理临时件声明进 git index→事后卫生门红且污染提交面。→ 过程件只落仓库外；波后编排者必跑 git reset 清 index。详见 apply §九。
- **R27 编排纪律无载体**：次序/授权/凭据/释放四类承诺只散在 skill 与会话记忆里，计划完成时未固化成编排文档→派发无单一依据、等待表无人消费、"完成"无对照物（为 R18/R19 的共同上游）。→ 阶段 4 强制产出 ORCHESTRATION.md（金字塔式），每次派发前重读对齐、单后回填台账。详见 apply §〇。
- **R28 域级派发过粗**：整域当一个派发单时，域内少数已解锁孙任务要等其余卡住项；释放事件按域登记则常无“可整域派发”的候选，R18 的当场消费落空。→ **task 级充分并发是自然行为而非选项**：规划时就按文件簇切到孙任务粒度，并发准入=文件簇零相交（同文件必合单、异簇全并发，波内全部可并发单同时派发）；拆单须先记解锁收益。详见 apply §十。
- **R29 verify 后置**：验收面（点名测试/负向锚/消费者证据）到完成时才定，或以追认缩水替代原任务验收面（“真实源推后”“结构见证替评估”）→勾选与原承诺脱钩，返工到中期复审才暴露（23 叶补差重开实证）。→ 验收锚三要素随任务行前置；负向锚具名化为勾选硬门；缩水＝重开。详见 apply §十一。
- **R30 波后无独立偏差评估**：波次收尾只做编排者自验/信汇报即结账，或把验证整体拖到终态评审→S1/S2 类偏差（正式入口缺接线、测试补线冒充消费者）波内不可见，累积成中期返工（31 叶重开实证）。→ 波次执行完、任务结束前派验证子代理评估偏差（与实施者分离），返工止于波内。详见 apply §十一。
