## 第 0 章 一句话问题

我们要交付一个**反向传播算子**（给定损失对各输出的梯度，算出对各输入的梯度），
它跑在华为昇腾 NPU 上。做完之后必须回答一个看似简单的问题：

> **这个算子，对了吗？**

本章之后你会看到：这句话在真实工程里有**六种以上**的"假的对"。
而识别它们不需要高深数学，只需要一点怀疑心 + 三个可以动手做的实验。

## 第 1 章 这个算子在算什么

### 1.1 GDN 反向是什么

GDN（Gated DeltaNet）是一类线性注意力模型。它的前向按 **chunk（块）** 处理序列：
把长度为 `T` 的序列切成块；整除时 `NC = T / C`，每块 `C` 个 token（`T=8192, C=64`，即 128 块）。非整除时需要尾块算法；当前 v3 relay 明确拒绝，不能把拒绝测试当成尾块功能通过。

块与块之间要传递一个**状态矩阵** `H`（形状 `DV × DK`，我们是 `128 × 128`）：

```text
H_0 = h0                              （初始状态，可为零也可非零）
γ_r = 本块从第 0 个到第 r 个 token 的 g 的累计和
α_c = exp(γ_last)
对第 c 块：
    H_{c+1} = α_c·H_c + Vnew_c.T @ Kt_c
```

这里状态 H 为 `[DV,DK]`，不要与 batch 中的 head 数 H 混淆。块内中间量：

- `E_r=exp(γ_r)`，`th_r=exp(γ_last−γ_r)`，`Kt=th[:,None]*K`，形状 `[C,DK]`。
- `Γ_ij=exp(γ_i−γ_j)`；`L=tril(β[:,None]*Γ*(K@K.T), -1)`，`A=(I+L)^(-1)`，形状 `[C,C]`。
- `W=A@(β[:,None]*E[:,None]*K)`，形状 `[C,DK]`。
- `Vnew=A@(β[:,None]*V)−W@H_c.T`，形状 `[C,DV]`。
- `P=tril((Q@K.T)*Γ)`，`e_do=E[:,None]*dO`，分别为 `[C,C]`、`[C,DV]`。

这些是本项目参考实现的符号约定；先按维度检查乘法，再看公式的优化写法。

反向时方向相反：从最后一块往前，逐块传递一个"状态梯度" `Δ'`（我们也叫 `delta`）：

```text
Δ'_NC = 0                             （损失不额外依赖最终状态时）
对第 c 块（从后往前）：
    dvnew_c = P_c.T @ dO_c + Kt_c @ Δ'_{c+1}.T
    Δ'_c = e_do_c.T @ Q_c - dvnew_c.T @ W_c + α_c * Δ'_{c+1}
```

Δ' 的形状为 `[DV,DK]`。第一行的转置不能省略，即使 DK=DV 时形状检查无法暴露省略错误。

最后要输出**六个梯度**（我们的"六项"）：

| 名字 | 是什么的梯度 | 形状 |
|---|---|---|
| `dq` | 查询 Q | `[T, DK]` |
| `dk` | 键 K | `[T, DK]` |
| `dv` | 值 V | `[T, DV]` |
| `dbeta` | 门控标量 β | `[T]` |
| `dg` | 对数衰减 g | `[T]` |
| `dh0` | 初始状态 h0 | `[DV, DK]` |

**关键结构**：`Δ'` 是矩阵伴随递推量（当前块算出的状态梯度供更早块使用）。`dk` 本身只写不读；`dg` 另外使用后缀累计 `carry`。单块通过不能证明跨块传播正确。

### 1.2 参考值（golden）从哪来

我们没法"直觉判断"一个 128×128 的梯度矩阵对不对。所以标准做法是：

1. 用纯 Python/NumPy 写一份**完全按数学公式**的实现，跑在 CPU 上，用 **64 位浮点（fp64）**；
2. 让 NPU 的算子跑同一批输入（fp16）；
3. 比较两者。

这份 CPU 版就叫 **golden**（金标准）。它的可信度决定一切——第 3 章会讲它怎么也会骗人。

### 1.3 为什么要小块 + 多块

- **小块**（C=64）才能塞进芯片的片上缓存；
- **多块**（128 块）才代表真实序列长度。

于是问题天然分成两半：**单块内算对**、**块与块之间传递对**。
后文的八条历史误判中，多项涉及只验证局部，却把结论扩成整条链。

## 第 2 章 "对"是什么意思：三把尺子

设 golden 为 `g`，算子的结果为 `a`，逐元素误差 `e = |a - g|`。工业界有三把常用尺子：

### 尺子 1：最大绝对误差 `max_abs`

```
max_abs = max(e)
```
**优点**：直观。"最大就差这么点。"
**缺点**：与数值量级绑定。梯度值本身在 1e-3 量级时，`1e-3` 的误差是 100% 错；在 1e3 量级时是 0.0001% 错。

### 尺子 2：归一化相对误差 `rel`

```
rel = max(e) / max(|g|)
```
**优点**：按参考整体幅值归一化；比较不同形状和机器时，仍要说明输入、精度和参考口径。参考全零时需要另定绝对误差契约。
**缺点**：它是"相对整个矩阵的最大值"归一化，**不是逐元素**的。少数超大元素会掩盖多数元素的问题。

### 尺子 3：逐元素匹配率 `matched_ratio`

```
matched_ratio = mean( e <= atol + rtol * |g| )     # 逐元素判断
```
本项目讨论过的 fp16 参数：`atol = 2^-14 ≈ 6.1e-5`，`rtol = 2^-9 ≈ 1.95e-3`，门槛 `≥0.99`。这不是所有算子的通用标准；dbeta/dg 为 fp32 输出，现有测试还使用对应 dtype 的绝对误差门。
**优点**：最接近"大部分元素都对"的直觉。
**限制**：是否通过取决于每个误差与该位置允许值的配对。误差可能来自更大的中间量，但这不能证明门槛在数学上不可达到；第 8 章解释旧推断为何不成立。

### ⚠️ 最重要的一条

**这三把尺子不能互相换算，也不能混着用。** 本项目就吃过这个亏：
曾经把"`T=256` 的 `max_abs`"与"`T=64` 的 `rel`"相除，得出"改善 7~22 倍"——
那个倍数里其实混着"梯度的最大幅值"和"序列长度比"两个因子，结论完全作废。

> **比较口径**：不同尺子分列并注明；只有分子、分母、输入和测量对象一致时才讨论改善倍数。

## 第 3 章 golden 本身也会骗人

golden 是 CPU 上的 fp64 实现，听起来最可信。但它有两类问题：

### 3.1 仓里可能同时存在两份 golden

本项目就有两份：一份在测试文件里，一份被"合并"进单文件示例里。
**如果两份不一致，你比较的就不是"算子 vs 数学"，而是"算子 vs 某一份实现"**。

**怎么办**：先在 CPU 上让两份 golden 互相对齐（同输入，逐项比），误差应到 1e-12 以下。
我们实测是 `≤3.1e-15`，这一步花了几秒钟，却排除了一个巨大的可能性。

### 3.2 测试里可能有"用 golden 替代被测件某一段"的开关

历史测试曾将 `GDN_V3_GOLDEN_H` 默认设为 `"1"`；当前 `test_gdn_bwd_v3.py` 默认已是 `"0"`，打开时打印警告并限制 B=H=1。打开的作用是：

> 把 golden 算出的中间状态 `H_in` 和矩阵 `A` **直接灌进**算子，
> 后半段不再消费我们自己那两个子算子（`scan1`、`solve_a`）的结果；原生前置计算仍可能执行。

于是那一列"六项都通过"验的其实是：**"在中间量已经正确的前提下，后半段对不对"**。
它没有验原生整条链路。历史报告若未披露这个开关，就会扩大结论范围。

**被替换的是被测计算链的中间量，不是误差公式的分母。** 替换实验可用于隔离问题，不能作为原生整链验收。

> **验收口径**：整链验收走原生路径；参考替换实验单列，并明确未覆盖哪些前置结果。

## 第 4 章 实验一：父张量连续，不代表切片连续

这是我们在**真机上被拒了两次**的原因，但它在你的笔记本上 5 行就能复现。

```python
import torch
torch.manual_seed(0)
q = torch.randn(1, 16, 512, 128)          # 一个"连续"的张量
print(q.is_contiguous())                  # True

sl = q[:, :, 0:64, :]                     # 切中间那一维（时间维）
print(sl.shape)                           # (1, 16, 64, 128)
print(sl.stride())                        # (1048576, 65536, 128, 1)
print(sl.is_contiguous())                 # False  ← 意料之外？
assert q.is_contiguous() and not sl.is_contiguous()
```

为什么会这样？"连续"的含义是：**按行优先顺序，元素在内存里是紧挨着的**。
切片之后形状变成 `(1,16,64,128)`，但内存里每一行仍然是"跳着"取的——因为原来第三维长度是 512，
现在只要前 64 个。于是：

```
需要的 stride（连续）:  16*64*128,  64*128,  128,  1
实际的 stride        : 16*512*128, 512*128,  128,  1
                ↑ 这两处对不上，所以不连续
```

**最坑的一点**：如果 `H=1`，这两个"对不上"的维度长度都是 1，stride 不参与判定，

```python
import torch
torch.manual_seed(0)
q1 = torch.randn(1, 1, 512, 128)
assert q1[:, :, 0:64, :].is_contiguous()
print(q1[:, :, 0:64, :].is_contiguous())  # True  ← 碰巧连续
```

在上述 **B=1** 的切片案例里，只测 H=1 看不到这个间隙。历史真机报错为 `Input tensor at index 0 must be contiguous`；不要把这个特例泛化为所有 H=1 张量都连续。

### 你要记住的

- 让"父张量"连续（`q = q.contiguous()`）**不能**让它的中轴切片连续；
- 连续化必须落在**切片之后**；写成一个统一的小函数，别散落十处：

```python
import torch

def _contig(x):
    return x if x.is_contiguous() else x.contiguous()

x = torch.arange(24).reshape(1, 2, 4, 3)
sliced = x[:, :, :2, :]
assert _contig(x) is x
assert _contig(sliced).is_contiguous()
assert torch.equal(_contig(sliced), sliced)
print('连续化保留数值')
```

- 对已经连续的输入，该函数原样返回；这包括上面的 B=H=1 特例，不代表所有 H=1 切片都免拷贝。

## 第 5 章 实验二：形状覆盖 ≠ 参数覆盖

这是人为注入“漏累加”的 CPU 教学演示，用来说明分支覆盖；**不是真实 solve_a 后端故障的微观复现**。

### 5.1 一个"只在多块时出错"的函数

```python
import numpy as np

def kk_split(K, BK, bug=True):
    """把 K 的列按 BK 分块，累加各块的 K_block @ K_block^T。"""
    C, DK = K.shape
    out = np.zeros((C, C))
    for i in range(DK // BK):
        blk = K[:, i*BK:(i+1)*BK]
        if i == 0:
            out = blk @ blk.T          # 第一块：初始化
        else:
            if bug:
                pass                   # ← BUG：忘了把第二块累加进去
            else:
                out += blk @ blk.T
    return out

np.random.seed(0)
K64  = np.random.randn(64, 64)
K128 = np.random.randn(64, 128)

ref64  = K64  @ K64.T
ref128 = K128 @ K128.T

print("DK=64,  BK=64 :", np.abs(kk_split(K64,  64) - ref64).max())   # 0.0      ← 对
print("DK=128, BK=64 :", np.abs(kk_split(K128, 64) - ref128).max())  # 81.78    ← 错
print("DK=128, BK=128:", np.abs(kk_split(K128, 128) - ref128).max()) # 0.0      ← 又对了
assert np.array_equal(kk_split(K64, 64), ref64)
assert not np.allclose(kk_split(K128, 64), ref128)
assert np.allclose(kk_split(K128, 64, bug=False), ref128)
```

（上面三个数是在 `seed=0` 下实测的输出；你跑出来应当是同一组。）

看清楚这个模式：

| 配置 | 循环跑几次 | 走没走到 `i>0` 分支 | 结果 |
|---|---|---|---|
| `DK=64, BK=64` | **1 次** | 没走到 | 对 |
| `DK=128, BK=64` | 2 次 | 走到了 | **错** |
| `DK=128, BK=128` | **1 次** | 没走到 | 对 |

所以“测了 DK=64/BK=64”只支持单次迭代路径，**没有覆盖多轮累加、非零偏移和 buffer 复用**，并非什么都没验。

### 5.2 真实版本

历史 `solve_a` 使用 `for i in T.serial(ceildiv(DK, BK))`，relay 曾传 BK=64。DK=64 时没有覆盖非零列偏移和后续累加分支。真实代码并没有忘写累加；组合搬运路径的异常与 toy 的人为漏项不同。

当前 relay 保留 BK=DK 绕行；v2 源码已改为直接 GM→L1，但候选修复尚待 T3a 上卡验证。单文件 example 内联前置件仍是旧搬运形式，现有同步脚本没有覆盖这一段。

实测后果：

```
DK=64  → 中间量 A 的误差 5.9e-05 （对）
DK=128/BK=64 → 中间量 A 的误差 1.39e-01（该批前置件误差很大）
改为 BK=128（块数回到 1）→ 5.96e-05 （又对了）
```

> **规则**：每个 `for ... in T.serial(ceildiv(X, BX))` 形状的循环，
> 测试矩阵里**至少有一个"块数 > 1"的用例**；日志里同时打印 `X / BX / 块数`。

## 第 6 章 实验三：你的探针会替别人认错

排查时我们会写"探针"——一小段脚本，喂一个已知输入，比较算子输出与参考。
问题在于：**探针自己写错时，它不会说"我错了"，它说"对方错了"。**

### 6.1 一个小演示

```python
import numpy as np

x = np.arange(24, dtype=np.float64).reshape(4, 6) / 10
part = x[:, :3]
actual = part @ part.T                 # 待测件只计算前三列的贡献
right_ref = part @ part.T
wrong_ref = x @ x.T                    # 探针误用了全宽参考
right_error = np.abs(actual - right_ref).max()
wrong_error = np.abs(actual - wrong_ref).max()
assert right_error == 0
assert wrong_error > 0
print('同一正确结果：正确参考通过，错误参考失败')
```

现在把 `probe` 里"忘了裁 ref"这类错误放到真实场景里：**它会稳定地报出一个很大的误差**，
而你第一反应一定是"我的算子坏了"。

历史上曾把“中间量 A 差 14%”与另一测试 dq 较小视为矛盾，后续发现比较范围、开关和形状并未充分对齐。中间量误差大也不必然使所有下游误差同样大。正确动作是复核两条实验的输入与参考路径，不先判探针或 kernel 有罪。

### 6.2 解法：每条探针都必须带一条"控制臂"

**控制臂（control arm）是有独立预期行为的对照配置。** 它帮助判断量具和环境，但一条通过不能证明目标分支也正确。

```
CONTROL name=A@64形  rel=5.9e-05  PASS     ← 先证明探针本身是准的
TARGET  name=A@128形 rel=1.39e-01 FAIL     ← 这时这个 FAIL 才有意义
```

无控制臂的 FAIL 仍有信息，但通常不足以区分探针、输入、环境和被测件的责任；不是“信息量为零”。

实测比例（我们这一轮）：9 支自写探针里 **4 支第一次跑就暴露自身缺陷**——
`beta` 被误转成 fp16、改了输入却没重算 golden、按直觉写错某个 kernel 的参数顺序、
参照取错了范围。这是历史探针清单中的比例，不是所有调试任务的统计规律；对照臂自身也曾选错，不能宣称它让错误解释从未进入结论。

> **证据边界**：归因实验记录控制臂及其来源。回归可使用历史版本或独立参考作对照；没有名为 CONTROL 的日志行，不等于没有有效对照。

## 第 7 章 我们的八次误判（真实数字）

上面三章是原理。下面是把原理套到真实故事上——**每一条都是我们自己犯的**，
按发现顺序排列，附带"如果当时知道什么就能避免"。

| # | 我们当时以为 | 实际 | 一条能避免它的检查 |
|---|---|---|---|
| 1 | "精度改善了 7~22 倍" | 两把尺子混用，倍数里混着"梯度幅值"与"长度比" | 一张表只用一把尺子（§2） |
| 2 | "`dk` 参与块间递推，所以要给它加 fp32 中转" | 读错代码：`dk` 只写不读，真正的递推量是另一个变量 | 结论要能指到具体行号，且被代码证伪过一次 |
| 3 | "把数据从片上缓存写回显存的函数不支持 fp32" | 实际是源/目标 dtype 不一致；那个函数是泛型的 | 报错原文 + 模板定义一起读 |
| 4 | 示例测试“通过” | 只在 `rel >= 5e-3` 时失败，NaN 可绕过；聚合 max 还可能吞 NaN | 在聚合前验证有限性，再判断阈值 |
| 5 | “六项都 <5e-3，多块可用” | 历史该列用了 golden 中间量替换；当前默认已关 | 原生与替换实验分列（§3.2） |
| 6 | "目标形状跑通了" | 只证了"没有 NaN / Inf"（`isfinite`），没量精度 | "跑通"必须同句给出精度或写"未验" |
| 7 | "多 head 不支持" | `H=1` 也一样错；head 数、块数、初始状态、golden 全被逐个排除 | 一次只改一个变量 + 控制臂 |
| 8 | “128 维 GEMM 普遍不准” | 仓内同宽矩阵乘有通过反例；不能把局部问题归于所有 128 维收缩 | 查已存在的反例，再隔离具体前置件和路径 |

第 8 条尤其值得记住：它不是"没做实验"，而是"**没有检索已有证据**"。
一条 grep 就能省掉一次上卡（每轮 5~15 分钟）。

## 第 8 章 最大误差不能证明匹配率永远不可达

本章撤回旧版“深链无论怎么优化都到不了 0.99”的结论。历史 `dk` 曾有 `max_abs=1.358e-3`、`|g|max=3.70`，因此全局 rel 约 `3.7e-4`；这只是在 fp16 单位舍入 `2^-11` 附近的量级，不是逐元素误差下限。

逐元素判据为：

```text
|a_i-g_i| <= atol + rtol*|g_i|
```

幅值 0.05 的位置可能只允许约 1.6e-4 的误差，但我们不知道该位置实际误差是多少。**某处最大误差为 1.358e-3，不代表每处都有这个“底噪”。**

即使设 B=max_abs，条件 `|g_i| >= (B-atol)/rtol` 也只是保证通过的充分条件。统计满足它的位置占 96%，不能推出匹配率上限 96%；不满足的位置仍可能误差为零。

[实验证据教材](learning_path/05-experimental-evidence.md)给出 CPU 反例：相同最大误差、相同参考，匹配率可以分别为 0.999 和 0.001。故不存在仅由 max_abs 推出的上述不可达结论。

深链误差确实可能来自中间量、相消与累计。判定需要逐元素配对分布、参考独立性、输出 dtype 和实际训练敏感性。多个指标可共同作为契约，也可有诊断列；改变验收门槛需要明确裁决，不能靠这一错误论证自动放宽。

## 第 9 章 四条纪律（把上面的内容压缩成可执行的东西）

1. **一条结论 = 数字 + 适用范围 + 对照组**
   适用范围必须写清四格：**形状 / dtype / 输入分布 / 开关状态**。
   例：`在 B1 H16 T8192 DK128 DV128/C64、主体 fp16、g/beta fp32、rsa seed=7 的 -abs(randn)*0.5-0.05 衰减输入、原生前置件下，历史 dk rel=4.29e-03`。
   填不满四格的结论，只能算"某次跑里看到了"。

2. **目标形状排在用例列表第一行**
   小形状先跑通是合理的工程习惯，但**交付判据必须在目标形状上**。
   目标形跑不动就如实写"未验证"，**不许用小形状顶替**。

3. **探针先有控制臂，再问新问题**
   控制臂不过时先复核对照及环境；保留目标观察，不直接作唯一归因或宣称整批通过。

4. **一次只改一个变量，且判读规则写在跑之前**
   跑完只看对账，不事后解释——事后解释是"把结果讲圆"，不是"验证"。

这四条已写成草稿（见 `docs/drafts/acceptance-gates-pending-validation/`）。
但请记住：**它们还没在真实任务里完整走过一遍**，所以只能当自查清单，不作权威。

## 第 10 章 自测（8 题，答案在题后）

1. `q` 的 `is_contiguous()` 是 `True`，那么 `q[:, :, 0:64, :]` 一定是连续的吗？
2. 为什么 `DK=64, BK=64` 的测试发现不了 `BK` 分块循环里的 bug？
3. 你的探针在目标形状上报 `rel=0.14`，在已知好的形状上没跑过。你应该先做什么？
4. 一个判据 `rel >= 5e-3`，当 `rel` 是 NaN 时会怎样？
5. "`isfinite` 全为真"能说明什么？不能说明什么？
6. 两个指标：`T=256` 的 `max_abs=1.3e-2`，`T=64` 的 `rel=5.5e-4`，能直接相除说"改善 24 倍"吗？
7. 为什么"用 golden 替掉某段"的开关如果默认打开，会让验收失效？
8. 你想到一个"很有解释力"的假设，下一步该做什么？

**答案**

1. 不一定。父张量连续不传导给中轴切片；`H=1` 时会"碰巧"连续，所以小测试发现不了。
2. 因为 `ceildiv(64,64)=1`，循环只跑一次，`i>0` 的分支从未执行——形状覆盖了，参数路径没覆盖。
3. 先给探针加控制臂（跑一个已知好的配置）。控制臂不过，0.14 这个数不可引用。
4. NaN 的顺序比较为 False，但 `NaN != NaN` 为 True。先检验有限性再检验阈值；还要防止 `max(0.0, NaN)` 在聚合时把 NaN 吞掉。
5. 能说明"没有 NaN/Inf 传播问题"；不能说明精度。`finite ≠ accurate`。
6. 不能。两把尺子不同，且 `T` 不同，倍数里混着梯度幅值与长度因子。
7. 因为那一列验的是"给定正确中间量之后的下游链"，整条链路没被验过，而报告若没写这一点，读者会以为是整链。
8. 先搜自己的笔记/仓里有没有反例（本项目就有一条反例让这个假设在发车前作废）；然后设计一个"只改一个变量 + 自带控制臂"的实验。
