评估对象为 GitHub 仓库 SpellingDragon/system-one-study：主页创建于 2026-10-05，本地克隆首提交 `fccbf79` 为 2026-10-04 凌晨[^1^]；截至评估基准 HEAD `b4a399f`（2026-10-10 13:10 +0800）共 61 提交、git 跟踪文件 1140 个、仓体 63MB（含 git 史 14MB），其中 31MB 为 CI 用 tiny 语料二进制[^2^]。README 自我定位为"学习项目"与"agent 驱动软件工程的活教材"[^3^][^4^]，正文两幕：第一幕 `scratch/`（P1，自称已归档）禁第三方预训练权重从零造（自训 BPE、约 40M 决策引擎、自写 TileLang 内核）；第二幕 `release/`（P2，进行中）在 Qwen3.5-0.8B 基座上"造得更好"，引入昇腾 910B 内核栈[^5^]。开发以多级 OpenSpec 变更（规划审覆盖、执行审一致、验收审证据）与子 agent 五段战报制度组织[^4^]。

### 1.2 方法与证据标准

#### 1.2.1 八维并行审计与编排者实证复核

评估采用"八个独立审计代理并行 + 编排者实证复核"两段式：八维覆盖 README 主张核验（Dim01）、模型代码（Dim02）、内核链（Dim03）、第二幕生产链（训练与评测方法学，Dim04）、工程实证（亲跑 README 命令，Dim05）、合规与编排方法论（许可证 + OpenSpec 制度，Dim06）、外部事实核查（Dim07）、git 法医（Dim08）[^6^]；编排者再在只读工作区对全部 blocker 级发现做本地实证复核，手段如对第一幕 `scratch/` 的语义化 grep（GQA/kv_head 零命中）[^7^]、按 README 原样跑 pytest（复现收集期硬错误）[^8^]、OpenSpec 任务清单逐文件计数[^9^]、自训 BPE 词表实测 token 编号[^10^]。工程实证环境为 Linux 容器（Python 3.12.12，2 核 / 4 GiB 内存）[^11^]。

#### 1.2.2 证据分级表

本报告对所有主张按下列四级归档：

| 级别 | 采信条件 | 典型证据形态 | 处置方式 |
|---|---|---|---|
| A | 编排者本地实证复核，命令可重放 | grep 命中数、pytest 退出码、逐文件计数、词表实测 | 作为定论依据 |
| B | run 档记录与代码、外部记录相互咬合 | metrics.jsonl ↔ 代码路径 ↔ GitHub API | 采信并注明证据链 |
| C | 单一来源，无第二方佐证 | 仓库自述、单份 run 结论 | 降级标注"待证" |
| D | 资产或环境缺失，无法独立验证 | 权重/主语料不在仓、无对应硬件 | 记"证据缺失"，不作判决 |

该分级把"证据强度"从"结论方向"剥离：A 级既用于坐实问题（如复现 pytest 收集期硬错误，证"296 绿"不可复现[^8^]），也用于坐实真实性（如自训 BPE 词表实测证实"字母单 token"性质为真[^10^]）；账码咬合的 B 级则用于坐实内部自洽（如主训练 run 的 tokens\_seen=131,072,000 与 2000 步 × 65,536 token/步精确吻合[^12^]）。C 级主张获第二来源或本地复核即升入 B/A；D 级无论叙述多详尽都不升级，构成第 2 章采信上限。

红线两条：其一，README 自述一律不直接采信，例如"13 子域 72 孙任务全勾对账"经逐文件计数实测为 82 条孙任务（含嵌套口径；严格顶层口径 80）、仅 56 条已勾[^9^]；其二，查不到证据的主张不判为假，记"证据缺失"，与"判定为假"严格区分。

#### 1.2.3 评估边界

本环境无 Apple MPS 与昇腾 910B 硬件：涉硬件的主张（如 P50 5.8ms 延迟、910B 内核数值）只能核账目一致性，不能重跑验证[^13^][^14^]。评估基准为 2026-10-10 的 HEAD `b4a399f`，其后提交不覆盖。外部事实以公开 API 与页面为准（如 tilelang#3448 互动时间线经 GitHub API 独立印证[^15^]），不随自述更新延伸。

#### 2.1.2 "910B 自研算子栈……吃自己狗粮的完全体"不成立

README.md:22 原文："910B 云端训练推理，七类算子手写 TileLang 方言件（本地 CPU 对拍 20 绿、GDN 反向 partial 如实挂账）——吃自己狗粮的完全体"[^20^]。逐词对账的结果：

- **生产件从未在 910B 编译过**。`release/ascend/kernels/` 共 8 件 `*_asc.py`，本审计 grep 实测其中 7 件含 `T.SimtVF`（唯一例外是 LoRA 旁路件）[^21^]；项目自己的 INVENTORY §5 判读原文为"七件 kernel 全部用 T.SimtVF，没有一件是纯 AIC 且零向量"[^22^]。SimtVF 是 950 代 SIMT 面 intrinsic，在 910B 上零存在——这批"生产件"唯一被验证的形态是本地 CPU(c) 后端对拍（20 passed，误差 ≤1.4e-06）。
- **真机数值绿的 3 件是未接线的实验件**。rope（rel=3.13e-08）、attn_sw 的 softmax 侧件（rel=1.41e-07）、GDN 的短卷积段（rel=6.35e-08）绿在 `port910b/attempts/` 下的标量改写件，与生产件不同源，production/serving 无任何 import 引用它们[^23^]。
- **cube 面双双崩于真机且已升格致命缺陷**。oncard-wave1 run 的 metrics 记录 gemm 与 gemm_bwd_dw 双双触发 `aicore exception 507015`（DMA 非法访问型崩溃）[^24^]；HEAD 提交 `b4a399f` 的提交信息即"cube-face dual aicore-507015 escalates V1/V2 to fatal-defect class"[^25^]——矩阵乘这层地基在卡上连一层都过不了。
- **云端训练实际走的是 torch_npu 底座+HF 前向**。`sft.py` 的"被否方案四"原文自承："把 backbone 前向也换成 p2-13 内核——本地既无昇腾卡，p2-13 的 GDN 反向还挂在 partial……故 kernel 开关目前只接管 SFT 自己新增的 LoRA 旁路，backbone 前向仍是 HF 实现"[^26^]。

结论：自研内核在 910B 训练/推理链中**零接入**，"完全体"是进行时伪装成完成时。GDN 反向 partial 的挂账机制本身（接口面标记+机器阻塞账+专测）是教科书级诚实，但它同时正是"狗粮吃不成"的直接原因——README 引用了诚实的局部，拼接出不实的整体。证据级：A。

README.md:44 给出的验收命令是 `cd ../release && .venv/bin/python -m pytest tests -q -m "not integration"`（注释自称"第二幕 296 绿"）[^30^]。实测在当前 HEAD 上该命令**收集期即硬错误，0 个测试被执行**：`release/tests/test_backends.py:26-29` 把 `@pytest.fixture(autouse=True)` 对同一函数重复装饰了两次（中间夹一个空行，疑似合并事故），pytest 8.4.2 与 9.1.1 均报 `ValueError: @pytest.fixture is being applied more than once`，RC=2[^31^]——与依赖版本漂移无关，是仓库自身缺陷。绕过该文件后实测 259 通过/12 失败；补装未声明依赖后 265 通过/6 失败；修复副本单独跑 test_backends.py 得 11 通过/4 失败（4 个失败用例实为 MPS-only，Linux 上必红），最佳合计 **276 通过**，与"296 绿"存在无法弥合的差距[^32^]。静态计数亦不吻合：HEAD 上 `def test` 共 311 个；"296"仅与引入该说法的历史提交 `a814f54`（2026-10-06）的静态 `def test` 计数吻合，此后测试增长而 README 数字未同步[^33^]。一个能活着入库的收集期硬错误同时证明：这 296 个测试自入库起从未在任何 CI 上被完整执行过（见 2.2.3）。证据级：A。

README.md:12/43 称第一幕"四轴评测一键复现（repro_p1.sh，exit 0 即 DoD）"[^36^]。实测裸克隆原样执行，阶段 0 前置体检即拒跑：`✗ 缺转写训练集 bench/p1-09/sft_train.jsonl；先跑：python -m sys1.data.transcribe`，REPRO_RC=2[^36^]。根因：`bench/` 整目录被 `.gitignore:10` 排除[^37^]，SFT 转写集与评测集均不在克隆中；转写工具需要本地已有 XNLI/MASSIVE/星级评分三类外部数据集（`sys1/data/transcribe.py` 模块自述）[^38^]，脚本本身不下载任何数据。脚本注释自称"干净机器 <20 分钟"，但前提是用户已备好三个外部数据集副本——"一键"实为"三键加一个隐藏前置"。公平地说，exit 2 是诚实拒跑而非假绿，且仓内留有作者机器上的既往成功产物（5 份 eval 报告）；但这些产物的 chain 字段指向作者本机绝对路径，第三方无法从仓库内容独立重放[^39^]。证据级：A。

#### 2.2.2 权重零入库+主语料缺席+多处 data_revision: UNPINNED

"从零训练"的第三方验证链条有三处断点。其一，全仓无任何模型权重（`.gitignore` 排除全部权重格式，政策为"按来源+commit 重建"），P1 最终模型与 P2 基座权重都只能靠重训[^40^]。其二，主训练语料 corpus_main（117,489,266 token，约 1.17 亿）**不在仓内**——仓内只有 4 个共约 31MB 的 tiny 语料 shard，第三方最多复现 tiny 档（S1 仅 20 步），复现正式档意味着先重建 1.17 亿 token 语料再在 Apple Silicon 上重跑约 21 小时[^41^]。其三，多份关键 run 的 config 写 `data_revision: UNPINNED`（含两份产出头条数字的 eval 报告），违背项目自订的 data_rev_pin 铁律，两次评测究竟用了哪份数据（外部 test 集还是 SFT 留出集）仓库不可考[^42^]。叠加结果是：README 的四个头条数字只能信 runs/ 转抄，无法低成本复核。证据级：A（断点存在性）；D（头条数字的独立验证）。

#### 2.2.3 README 快速上手四步实测仅第一步成立

README.md:40-45 的四步快速上手，实测账目：第 1 步（scratch 装依赖）在换用镜像源后成立；第 2 步（ci.sh 四门禁）在本审计环境因挂载与内存限额失败，属环境伪影，不追责；第 3 步（repro_p1.sh）如 2.2.1 所述 exit 2；第 4 步（release 测试）直接引用 `release/.venv/bin/python`，但快速上手**从未创建 release 的虚拟环境**，release/README 的启用步骤甚至硬编码了作者私人路径 `$HOME/miniconda3/bin/python3.12`（release/README.md:21）[^43^]。补齐环境后又会撞上三道墙：2.1.4 的收集期硬错误；7 个用例因 `modelscope`/`transformers`/`PIL` 未在 `[dev]` 依赖中声明而失败[^44^]；以及 `.github/workflows/ci.yml` 只跑 scratch 的门、**release 的 300+ 测试零 CI 覆盖**——这正是双重装饰器能活着入库的结构性原因[^45^]。证据级：A。

### 2.3 重大：代码实现与声明的偏差

#### 2.3.1 "RoPE/GQA/FFN 一手敲出来"中 GQA 不实

README.md:11 称第一幕"自己写 ~40M 因果 decoder（RoPE/**GQA**/FFN 一手敲出来）"[^46^]。GQA（Grouped-Query Attention，分组查询注意力，即多个查询头共享键值头）在实现中不存在：`scratch/sys1/model.py:205` 为 `self.qkv = nn.Linear(config.d, 3 * config.d)`，Q/K/V 同宽同头数，是普通 MHA；全仓 grep `GQA|kv_head|n_kv` 于 scratch/ **零命中**[^46^]。RoPE 与 FFN 两项核验为真（数学正确、与对拍参考同式），唯独 GQA 一词多写了——一行字里掺进一个未实现的架构名词。证据级：A。

#### 2.3.2 "~40M"口径不明——实际 54.2M

`model.py:57` 与 `mps_main.yaml:21` 均标注"~40M 参数"[^47^]。按 mps_main.yaml 配置（d=512、L=12、heads=8、vocab=16000、ffn_mult=4、bias=False、lm_head **不共享**）逐项核算：tok_emb 8,192,000 + 12 个 block 共 37,828,608 + final_norm 1,024 + lm_head 8,192,000 = **54,213,632（54.2M）**；只有按"非嵌入参数"口径才是 37.8M，勉强≈40M。两处代码/配置都未注明口径，按行业通行的总参数量口径，README 低估 35%。训练 run 的 tokens_seen（131,072,000 = 2000 步×65,536 token）与 metrics 末行精确一致，说明训练本身真实——问题纯在参数口径的标注缺失。证据级：A。

#### 2.3.3 TileLang 注意力内核链在 Decoder 前向不可达

这是第一幕最硬的实现级缺陷，三个环节形成死锁：①`Decoder.forward` **无条件**构造 visible 掩码张量传给每个 block（model.py:386，即使入参为 None 也会生成纯因果掩码）；②block 的内核门 `_kernel_ok` 在 `visible is not None` 时直接返回 False（model.py:211）；③于是可微内核四连（qkv→rope→attn_sw→proj）经公开 forward **永远走不到**，只有不查 visible 的 MLP gemm 内核能触发[^48^]。内核恰好唯一支持的"无 pad 纯因果"场景被这个门亲手挡死。连锁后果有二：README 引用的 parity 20/20 并非来自 Decoder 前向，而是 `eval/parity.py` 里**另行手工装配**的 `KernelForward` 类（绕开 Decoder.forward 重拼一层块）[^49^]；评测本地路径 `Decoder.load()` 没有 kernel_backend 参数、实际跑 eager torch，而报告头的 `backend=tilelang` 取的是环境偏好函数 `backends.active_backend(device)`，与被测模型实际前向路径无关（predict.py:400 vs 478）[^50^]——报告头标签与实际执行路径脱节。配套的"防假绿"断言查的是进程级全局编译登记表，同进程其他测试也能让它通过，证明力有限。证据级：A。

#### 2.3.4 OPD"per-token reverse KL（GKD 谱系）"三重名不副实

OPD 栈（p2-06）的设计自称"逐 token 粒度的 KL(p_teacher‖p_student)（reverse/mode-covering——Agarwal/OPD-survey 口径）"[^51^]。逐词核验：**①不是 per-token**——实现是判别式末位一次读出（选项级），opd.py 自述"token 在这里退化成一档"；**②不是 reverse KL**——`opd.py:521-546` 实现的是 $\sum_j p_t[j]\cdot(\log p_t[j]-\log p_s[j])$，即 $KL(p_{\text{teacher}}\,\|\,p_{\text{student}})$，这在标准术语与 GKD 原文（Agarwal et al.）中是 **forward KL**（mode-covering）；reverse KL 是 $KL(p_{\text{student}}\,\|\,p_{\text{teacher}})$，方向正好相反，design 把谱系引用张冠李戴[^52^]；**③不是 on-policy**——所谓 top-k"采样"是按分数降序的确定性截取（"与随机数无关"，opd.py:237-243），且 `collect_onpolicy` 在训练开头对整个数据集**只跑一遍**（opd.py:1018-1023），学生参数更新后子集与教师分布全程冻结——这是"初始策略上的离线蒸馏"，GKD 意义下随训练滚动再采样的 on-policy 要点完全缺失[^53^]。需要公平记录：散度数学本身实现正确（0·log0 约定、log 地板、掩码处理均无懈可击），mode-covering 的性质判断也对——错的是名字与谱系归属。此外该栈**零 run**：全部运行证据只是单测用假件验过编排逻辑。证据级：A。

#### 2.3.5 "A–Z=32..57"数字张冠李戴

README.md:14 把"A–Z=32..57 实测钉死"写进第一幕教训段[^54^]。实测第一幕自训 BPE 产物 `1003-s0-bpe-16k-*/tokenizer/vocab.json`：A–Z = **38..63**（连续）、a–z = 70..95，52 字母全部单 token——性质成立，数字错误[^54^]。"32..57"的真实出处是第二幕第三方 Qwen3.5 基座分词器（p201 run 校验记录，并固化为 `release/tests/test_assets.py:192` 的断言 `ids == tuple(range(32, 58))`）[^54^]。教训是 P1 的、数字是 P2 的，拼接方式会让读者误以为 P1 自训词表的字母号就是 32..57。证据级：A。

### 2.4 重大：统计与评测严谨性

#### 2.4.1 训练口对着评测 test 集

审计中最具后果潜力的发现：`release/sys1/eval/registry.py` 中 quality 轴的两个主力成员就是评测考卷——typed-decisions 登记 `split="test", axis="quality"`（:155 行段）、intern-decision 同样 `split="test", axis="quality"`（:175 行段），另有 cmmlu-subset test 与 clue-subset validation[^55^]。而 SFT 管线的默认配置（`sft.py:1048`）与全部 5 份 yaml（gate08b/scaling_06b/tiny_cpu/zh_mix_30/zh_mix_50）均写 `axis: quality`[^56^]；dev run 的 config 把四个集的 split=test/validation 原样记录在案。即：**全部已发生的 7 条 dev 训练 run 都在评测测试集上训练**。缓解因素同样有据：registry 已建独立 train 轴（`load_train_records()` 只回 split==train，缺 split 即报错）[^55^]；split 隔离有测试钉住（test_registry.py:322-375 断言 train id 不进六轴、训测 id 零交集）[^57^]；dev run 只出 loss 曲线、未出任何评测分，污染尚未兑现为报告数字。但项目自己写下的病灶修复闸——p2-05 tasks.md:49"C5 发射前置两闸：① 训练口改 axis: train……照旧即训测同集假分"——**至今未勾**[^58^]。机制修了一半（数据侧隔离完成）、消费侧仍是错口，正式档若按现配置点火即训测同集。证据级：A。

#### 2.4.2 统计功效不足

四处样本量问题叠加，使所有定量结论的置信度都应打折。①**全配置单种子**：五份 yaml 全部写死 `seed: 20261005`，无任何多种子扫描、bootstrap 或置信区间的代码与 run[^59^]。②**基线 n=24 单次**：双基线对照表（smoke24）每模型仅 24 题各跑一次，两模型 acc 同为 0.5833（14/24）——24 题下 acc 的 95% Wilson 区间约 ±20pp，Δ=+0.0000 这类数字在此样本量下几乎不携带信息，表中未给任何区间[^60^]。③**"+31.7pp"分母 n=40**：该头条数字出自 choice k=3 桶、n=40、26 命中，参照线是**随机基线 1/3**（0.6500 vs 0.3333）而非任何对手模型[^61^]；二项检验下超随机虽显著（p≈2e-4），但"越过参考线"的口径是"超随机+10pp 过程信号"，README 的表述会让读者误以为是越过竞品基线。④**needle 每档 1–4 题**："32K 召回衰减到 0.25"的逐题账目是 8192 档 1/2、32768 档 1/4、131072 档 0/1——32K 档仅 4 题、128K 档仅 1 题，0.25 的统计功效约等于零[^62^]。四处问题各自都不构成造假（数字与 run 档逐字一致），但合在一起意味着 README 的全部定量主张都建立在小样本、单种子、无方差估计的证据上。证据级：A（样本量事实）；B（区间估计为本审计推算）。

#### 2.4.3 评测集身份 UNPINNED+参考线为自定义常数

"参考线"的真实身份是项目自写常数：`scratch/sys1/eval/quality.py:39` 定义 `REFERENCE_MARGIN_PP = 10.0`，即"超随机基线 10pp 才算过程信号过关"[^63^]。自己定线、自己过线，构成自证循环的成分；同时 exit 0 的判定（report.py:100-109）根本不含质量阈值——`passed` 只查"轴非空+溯源未豁免+parity 未换人"，注释自承"质量/把握为呈现值，不参与退出码判定"[^64^]，即"exit 0 即 DoD"的含金量低于字面。两处需要公平的限定：该常数在代码与报告表头全程印出（`超参考线(+10.0pp)`），未伪装成外部标准；门禁弱化是写明的设计选择而非隐瞒。真正削弱可审计性的是 2.2.2 已述的 `data_revision: UNPINNED` 与 bench/ 缺席——参考线透明，但被评对象的输入身份不透明。证据级：A。

#### 2.4.4 选择性呈现：温度标定恶化案例未上门面

同一份产出 README 头条数字的 1006-aa36 评测报告还记录了一个负结果：54M 正式档上温度标定使 choice 轴 ECE 从 0.1175 恶化到 0.2267（Δ=+0.1092），标定温度顶到 clamp 上限 5.0，报告如实标注"改善：否"；noul 轴同样恶化（0.1562→0.1682）[^65^]。（校准 run 1006-s3-calibrate-962f 自身计量口径为 0.1709→0.2129，两处数字分属校准过程与正式评测档，非矛盾）[^66^]。README 只摘了第一幕 tiny 链的校准改善案例，对正式档的恶化只在"天花板"一句中含糊带过（"choice 校准反化"）。项目内部的记录是诚实的（负结果入库、未删），但门面叙事做了选择性采摘——对一个以"负结果不删"为荣的项目，读者有理由期待 README 同等待遇。证据级：A。

### 2.5 重大：合规与许可证缺口

#### 2.5.1 仓库自身无 LICENSE，对内却自称"MIT 树"

全树 `find -iname "LICENSE*"` 零命中，与 GitHub API 返回 `license: null` 一致——法律上默认保留所有权利，第三方克隆、复用、修改 `scratch/`、`release/` 代码均无授权依据[^67^]。矛盾点在 `refs/clone.sh:32` 的注释："禁拷贝代码入**本仓 MIT 树**"——仓库内部规则已把自己当作 MIT 项目治理，却从未落实一份 LICENSE 文件[^68^]。项目对他人许可证极其敏感（D11 白名单/黑名单、CC BY-NC-SA 资料"重写勿拷贝"），对自己的对外授权零管理——合规防线是单向的。证据级：A。

#### 2.5.2 CC BY-NC-4.0 教师蒸馏输出的权利论证缺失

D11（design.md:168-172）把"蒸馏教师打分"列入白名单，但**从未论证** CC BY-NC 权重的推理输出（logits/伪标分布）用于训练学生是否在许可范围内[^69^]。法律分析上该用途大概率成立（CC 许可约束的是权重本身的复制与再分发，模型输出一般不构成素材复制，且本项目为非商业个人学习），但仓库里找不到这段推理的任何记录。README.md:20 的"学生 100% 基于 Apache 2.0 基座（版权边界 D11 白纸黑字）"[^70^]只陈述了基座权重血缘，不能等同于"蒸馏产物权利无瑕疵"，易被误读为全链洁净；用内部规定（D11）为外部合规背书，是把家规当成了法律意见书。实际风险等级评估为低，但若学生模型日后被第三方引用或商用，"NC 教师蒸馏"将成为需要重新回答的问题，而仓库未留答辩材料。证据级：B（文档事实）；D（法律结论）。

#### 2.5.3 GLM-5.3-Flash API ToS 未分析

多处文书宣称 GLM API 伪标"红线合规"。追查"红线"定义，其出处是 `scratch/PRODUCTION.md:366` §11-4——"外部仅可作教师（离线产标/蒸馏），推理链路不得依赖第三方在线 API"[^71^]：这是项目自立的**架构纪律**，不是 GLM/Z.ai 的服务条款，"红线合规"实为"符合我们自己定的规矩"的同义反复。全仓 grep 无任何对 Z.ai/智谱 API 服务条款的分析；主流大模型 API 普遍限制"用输出训练竞争性模型"，GLM-5.3-Flash 输出能否用于学生训练从未核查。而执行侧已然就绪：3–6k 次全量调用已规划（p2-02 design.md:9）、key 已就位、试点 run 已完成[^72^]——合规审查滞后于执行就绪度。证据级：A（无 ToS 分析这一事实）；D（条款结论）。

### 4.1 第一幕数字链物理自洽

主训练 run `1005-s1-mps-main-dc8c` 的 metrics 末行记录 `tokens_seen: 131072000`[^109^]，而 config 写明 `max_steps: 2000`、`batch_size: 8`、`grad_accum: 8`、`seq_len: 1024`[^110^]，四者乘积经复算恰为 $2000 \times 8 \times 8 \times 1024 = 131{,}072{,}000$，逐位吻合[^111^]。step0 记录 loss 9.8506 且自注"随机初始化，未学过"[^109^]——对 16000 词表的均匀随机模型，理论交叉熵为 $\ln(16000) \approx 9.6803$[^111^]，9.8506 高出 0.17，方向与量级都符合"初始化噪声略高于理论下界"的物理图像；若伪造者随手填数，更容易出现低于 $\ln V$ 的破绽。时间链同样自洽：step0 时间戳 2026-10-05T04:35:10，step2000 为 2026-10-06T01:27:56，跨度 20.9 小时，每 20 步约 363–386 秒、吞吐稳定在 3.4–3.6k tok/s[^109^]——对 M3 Pro 的 MPS 后端跑约 54M 参数（总口径；非嵌入口径 37.8M，口径问题见 §2.3.2）[^112^]模型，这一吞吐处于合理区间，且全程无"性能突变"这类拼接痕迹。

最难伪造的是采样文本的质量档位。notes.md 逐条收录 8 条温度采样原文，起头"床前明月光，"接出的是"记 员 李春霞"这类半通不通的乱文[^113^]。这一证据的强度在于其**反向不可伪造性**：漂亮数字容易编，但"恰好烂到 131M tokens 训练的 54M 小模型该有的水平"——汉字能成串、语法不成句、偶尔撞出短语——要求伪造者对训练动态有精确直觉。Dim08（git 法医）审计将其判为"真实性最强的间接证据"，本章复核后维持该判断。

### 4.2 诚实文化真实落地

"诚实"在本仓不是 README 口号，而是可点名的入库记录，且其中多数对项目自身**不利**。温度标定 run `1006-s3-calibrate-962f` 的 notes 原文记录：choice 类温度顶到 5.0，校准 run 自身计量 ECE 从 0.1709 **恶化**至 0.2129（`improved: False`；正式评测档口径为 0.1175→0.2267，两处数字分属不同 run，见 §2.4.4），并明写"存在 ECE 变差类（样本小/弱模型，如实记录）"[^114^]——调参调坏了，照样入库记"否"。README 自述"run 不删——连三次空跑的曲线壳都留着，因为诚实比好看贵"[^115^]，审计实测在库零行 metrics.jsonl 共 5 个：其中 3 个即 README 自述的 needle 空跑壳（b46b/e6c8/v3-e4ba），另 2 个为多模态探针（e5a2）与 910B 盘点（885c）的未收工件，与自述一致[^116^]。DoD 核验 run 的 metrics 保留了一条 append-only 勘误：step0 记 `sxtasks_done: 77`，step1 不改原行、追加新行注明"step0 的 sxtasks_done=77 系编排者笔误；实测域内 66 + 一级 14，以本行为准"[^117^]——改数不删痕，这是账目文化而非修辞文化。

最重的一条是编排者把自己的翻车升格为制度。git 历史保留完整链条：`2b0c29b` 提交信息为"append-only erratum - P0-2a now genuinely verified (orchestrator's own false-green lesson)"，紧随的 `063f991` 自认"prior two commits claimed it without: orchestrator double false-green, now closed"，随后 `5fae0bd` 把教训写入 skill 成为反模式 R19（"commit-before-disk-verification；三输出核验先于任何勾选"）[^118^]。两天后又一条 `25f3472` 记录"R19 event caught"——制度在真实场景再次触发[^118^]。从"翻车"到"勘误"到"编号化反模式"到"再触发被逮"，四步闭环全部留在 git 史里。此外，性能负结果同样原样入库：TileLang Metal 内核热态全面慢于 torch-MPS 2–6 倍、可微链训练端到端 −8.0%（3048 vs 3315 tok/s，按两值复算；源 notes 原文记 −8.7%），归因明写"LN 主干走回退、attn 反向 torch 重算"[^119^]。在同尺度项目中，负结果通常消失在终端历史里；把这条负值写进永久账目并附归因，是这套证据文化最直接的物证。

### 4.3 代码层强制的防假绿与挂账

本仓的防假绿不是流程要求，而是代码层的强制结构。MPS 侧测试统一经 `_assert_ran_dialect` 双闸：先断言阻塞账为空（任何回退都会被 `record_blocker` 记账），再断言编译缓存里存在含指定片段的编译键——两道断言一起卡住"回退伪装成内核跑过"的通路[^120^]。昇腾侧 GDN 反向是挂账机制的完整标本：接口面常量 `BWD_STATUS = "partial"`（gdn_asc.py:30），`backward()` 先调 `ascend_env.record_blocker` 登记机器可见阻塞账、再走 torch autograd 对 `_eager` 递推求梯度[^121^]；专门测试 `test_gdn_cpu_backward_declared_partial_but_grads_are_correct` 同时断言三件事——partial 标记在场、阻塞账含 `gdn_backward` 记录、且"手工算"梯度与自动微分数值一致[^122^]。即挂账本身被测试守护：谁悄悄把 partial 改成 done，测试先红。判定纪律上，每次上卡/编译判决注入全新 `TILELANG_CACHE_DIR=$(mktemp -d ...)`，防止陈旧编译缓存制造"PASS 假绿"——这是 C 波"改 compat 头不失效"教训的制度化[^123^]。同时各 attempts 的 RESULT.md 统一明写"验收上限=compile PASS（本机无 NPU，未上卡）"，compile 与数值的区分在过程文档中执行严格[^124^]。需注明第 2 章 §2.3.3 的限定：第二闸查进程级全局登记表，同进程用例可交叉满足，单闸证明力有限——其价值在"双闸+挂账被测试守护"的结构，而非单闸强度。

这是全章唯一可由第三方独立复核的优点。仓内 `issue_upstream_910b.md` 存档了提交给 tile-ai/tilelang 的 issue #3448 全文，标注"SUBMITTED 2026-10-08"[^125^]；外部核验确认该 issue 真实存在、由同一 GitHub 账号提交、正文与仓内存档逐字一致[^126^]。时间线吻合到分钟级：仓内 metrics 记录上游 Contributor 回复的时间戳为 2026-10-09T17:07:53+0800，并逐义转写其三点内容（依赖未发布的 CANN 9.2.0、SimtVF 不被 910B 硬件支持、建议试 PTO 后端）[^127^]；GitHub API 显示该评论实际发表于 09:04:17Z（=17:04+0800），内部记录仅晚不足 4 分钟[^128^]。尤其关键的是不利细节的忠实度：仓内 notes 明写"我方回评（comment 6077898715）已删除，暂不回评"[^129^]——API 上该 issue 下恰只剩 1 条评论（id 6077845500，小于被删的 6077898715，编号相邻性吻合）[^128^]。一个项目把"我发了又删了回评"这种于己无益的细节如实入库，且与外部可查状态一致，其证据力高于任何漂亮数字。

### 4.5 D11 治理框架与数据底账

D11（StartLux 版权边界）的结构完整性在四类落点上同时存在：design.md:168–172 定义白名单（仅蒸馏教师打分/RL verifier 判分/对照评测推理三项）与黑名单（训练初始化/微调基座/权重再发布）[^130^]；编排 spec 把 D11 定为**合并硬拦项**，"触碰即拒 PR"[^131^]；变更 DoD 第⑧条要求"D11 版权边界自查（产出物零 StartLux 权量）"[^132^]；`.gitignore` 排除全部权重格式，`git ls-files` 实测无任何 safetensors/pt/gguf 入库[^116^]。白名单—黑名单—门禁—自查的四层结构，在个人学习项目中属于罕见的治理密度；需注明其边界：D11 是使用政策而非法律论证，NC 教师蒸馏的权利推演在仓库中缺席（详见第 2 章），本节只肯定其结构，不为其结论背书。

数据底账同样成制度：registry 对三个评测集同时钉短码 pin 与全长散列（防短码撞车），逐件 sha256 与实测字节落 manifest，连"git 协议被 TLS 掐断→改走 codeload 按内容钉版"的可达性取证都留在代码注释里[^133^][^134^]；训练/测试 split 隔离被测试套件钉死[^135^]。"实测字节+散列+取证注记"三件套意味着任何第三方可凭散列复验数据版本——这把"数据可信"从信任问题降格为校验问题，是同尺度项目中少见的工程自觉。

## 5. 跨维度洞察

第 2–4 章呈现的是逐条发现，本章只做一件事：提取**单个维度内部看不见、只有两个以上独立维度对照才浮现**的结构。方法声明：八个维度审计（Dim01 主张对账、Dim02 代码实现、Dim03 内核/算子栈、Dim04 第二幕生产链、Dim05 实测复现、Dim06 编排方法论、Dim07 外部核验、Dim08 git 法医）相互独立执行，一条模式须被至少两个维度各自撞上，才升格为本章洞察。

| 洞察 | 衍生维度 | 一句话模式 |
|---|---|---|
| 5.1 呈现层通货膨胀 | Dim01/02/03/04/05 | 完成时叙事系统性超前账目 1–2 阶段，账目本身全真 |
| 5.2 自我纠错不覆盖门面 | Dim06/08/01/02 | 回写闭环约束了过程，README 不受自家门禁管辖 |
| 5.3 诚实≠可复现 | Dim05/08/02 | 证据文化证明"没撒谎"，资产缺席使"可验证"落空 |
| 5.4 两幕可信度不对称 | Dim08/01 vs Dim03/04 | P1 经得起法医检验，P2 零端到端结果 |
| 5.5 教材价值悖论 | Dim03/06/08 | 最大诚意与最大问题是同一枚硬币 |

表 1 的维度分布本身携带信息：五条洞察无一依赖单一维度，这正是它们区别于第 2 章单点发现的判据。Dim08（git 法医）出现在四条洞察的证据链中——"叙事是否超前"本质是时间轴问题，只有提交史能回答；Dim04（第二幕生产链）出现在 5.1 与 5.4 两条洞察中，说明第二幕是门面失实与实绩缺口的双重高发区。后文的推导不是五份意见的并集，而是五组独立证据在同一结构上的交汇。

### 5.1 呈现层通货膨胀是系统性模式，而非个别笔误

**衍生自 Dim01/02/03/04/05 的证据交汇。**五个维度各自独立撞上同一结构：Dim01 发现"72 孙任务全勾"在 HEAD 任何口径下数不出来（实测 82 条仅 56 勾）[^136^]；Dim05 实测"296 绿"收集期硬错误、最佳 276 通过[^137^]；Dim02 发现 GQA 名不副实（实现为普通 MHA）[^138^]；Dim03 发现"完全体"的生产内核从未在 910B 编译[^139^]；Dim04 发现"向 StartLux-4B 蒸馏"的教师是 36.6M 随机权重脚手架[^140^]。关键在于第二层事实：每一处膨胀都能在仓内找到**正确**的底层账——p2-11 任务如实保持 0/6 未勾、sft.py 自述替身身份、INVENTORY 自判"七件全 SimtVF"[^139^][^141^]。推导：这不是造假（造假的特征是账目与门面一起美化），而是门面层与账目层执行了两套标准。含义：审计此类仓库时 README 只能当索引、不能当证据；以账目文化为卖点的项目在自家门面上放弃账目标准，使错位带上结构性讽刺。

### 5.2 自我纠错纪律约束了过程，没有约束门面

**衍生自 Dim06（R 系列闭环）、Dim08（勘误链）与 Dim01/02（门面数字失修）的对照。**流程内部的纠错机制真实有效：编排者把自己的假绿翻车经"勘误 commit→自认→编号化为反模式 R19→再触发被逮"四步闭环留在 git 史[^142^]；DoD 核验 run 的 append-only 勘误证明"改数不删痕"落到了账目层[^143^]。但同一时期，README 的 296、72、R1–R18 三个数字均不随代码同步（296 可定位至 10-06 起失修）——"296 绿"仅在引入该句的历史提交上成立[^136^][^144^]。推导：制度覆盖率 = 除门面外的全部。README 无 DoD 条款、无核验入口、无 CI 守护（CI 只门 scratch/，release/ 零覆盖）[^145^]；错误数字活到 HEAD 不是因为没人能发现，而是没有规则要求谁去发现。含义：制度有效性的边界就是适用范围的边界；评价一套方法论，应问"它不管辖什么"而非只问"它管辖得多好"。

### 5.3 内部诚实≠第三方可复现

**衍生自 Dim05（实测复现）、Dim08（资产法医）、Dim02（数据钉版）的合力。**证据文化证明的是"我没有撒谎"：负结果原样入库（温度标定调坏记 `improved: False`）、空跑壳保留（第 4 章已述）[^146^]。但"你可以验证我"在资产层不成立：bench/ 被 gitignore，repro_p1.sh 裸克隆 exit 2 拒跑[^147^]；全仓零权重入库，P1 正式档验证意味着重建 1.17 亿 token 语料并重跑约 21 小时[^148^]；两份产出头条数字的评测报告 `data_revision: UNPINNED`，数据来源身份不可考[^149^]。推导：内部诚实与外部可复现是两个独立属性——前者是记录纪律，后者是资产分发工程，本项目只完成了前者；repro 脚本的 exit 2 是诚实拒跑而非假绿，恰说明诚实是真的、复现是缺的。含义：对自评报告的信任应分两笔记账——"数字可信"可授予，"结论可复核"无法授予；可复现性这个核心卖点恰是实证最弱一环。

### 5.4 两幕可信度不对称，并列排版制造同等成熟错觉

**衍生自 Dim08/01（第一幕证据强度）与 Dim03/04（第二幕实绩缺口）的反差。**第一幕数字链通过物理一致性检验：tokens_seen=131,072,000 与"2000 步×8×8×1024"逐位吻合，step0 loss 9.8506 对理论下界 $\ln(16000)\approx9.68$ 方向与量级合理，20.9 小时时长与 M3 Pro MPS 吞吐自洽[^150^]——多环节咬合的数字链难以伪造。第二幕相反：RLCD 栈零实现、SFT 全部 7 条 dev run 为随机权重替身、OPD 零训练 run、生产内核从未在 910B 编译[^139^][^151^]——除基座接缝、教师打通与探针外无任何端到端"训练+评测"结果。推导：两幕处于不同证据等级，P1 可授予"法医级可信"，P2 只能授予"计划可信"。含义：README 将两幕并列排版，是全文对读者判断力最大的干扰源；评估应对两幕分别定价，任何把 P1 可信度外溢到 P2 的读法都不被证据支持。

### 5.5 作为教材的最大诚意与最大问题是同一枚硬币

**衍生自 Dim03（fatal-defect 留档）、Dim06（R1–R20 反模式库）、Dim08（空跑壳与假绿链）的汇合。**当产品评估，第二幕是过度承诺；当教材评估，其不可替代的价值恰来自对自身失败的暴露：cube 面 aicore-507015 崩溃升格为 fatal-defect 并写入 HEAD 提交信息[^152^]；三次空跑曲线壳入库不删[^153^]；编排者自身假绿的勘误链对外公开（5.2）；上游交涉中"我方回评已删"这类于己无益的细节与外部状态吻合[^154^]；"温度标定使 ECE 0.1175→0.2267"的负结果原样在库[^155^]。这些材料在成功项目的事后叙事中几乎必然被抹除，此处却构成别处看不到的"失败教学法"。推导：展示价值与审计风险同源——同一份暴露欲，在账目层产出教科书级诚实，在门面层产出 1–2 阶段的注水；门面注水削弱的正是教材价值本身：以 README 为地图的读者，学到的第一课就是错误数字（296、72、GQA）。含义：第 6 章的总体判断与建议将接过这个悖论——修复方向不是"少说"，而是把门面纳入自家已运转良好的门禁。

## 6. 总体判断与建议

### 6.1 总评：账目诚实、门面超前的真实学习工程

把第 2–5 章的证据压缩成一句话：**这是一个真实发生的学习工程，但其对外呈现层系统性地超前于自己的账目**。项目本体是单人（61 个提交全部同一署名）、6.5 天活跃窗口（2026-10-04 至 10-10）的高强度练习[^156^]。真实性置信度判为"高"，依据是内外双锚。内锚是第一幕数字链的物理自洽：主训练 run 的 `tokens_seen=131072000` 与配置四项乘积 $2000\times8\times8\times1024$ 逐位吻合，step0 loss 9.8506 相对理论下界 $\ln(16000)\approx9.6803$ 的偏离方向与量级一致[^157^][^158^]——伪造者难以凑对这类数字。外锚是 tilelang#3448：仓内存档与 GitHub 线上 issue 逐字一致，内部记录的上游回复时间与 API 时间戳差不足 4 分钟，连"我方回评已删除"这种于己无益的细节也与外部可查状态吻合[^159^]。

问题的分量同样不含糊。第 3 章核验表对 18 条主张（含外部引用）的判定为 10 成立、4 部分成立、4 不成立[^160^]；第 2 章确认 5 条阻断级主干叙事按字面均不成立——RLCD 栈零实现（p2-11 全 0/6）[^161^]、"296 绿"因收集期硬错误不可复现（实测最佳 276 通过）[^162^]、"72 孙任务全勾"实为 82 条仅 56 勾且"全勾"属已归档的第一幕[^163^]、"910B 完全体"的生产内核从未在 910B 编译[^164^]、文本蒸馏的教师至今是 36.6M 随机权重脚手架[^165^]。但问题清单的长度不改变项目的定性：每一处失实集中在 README 这个对外门面，底层 run 档本身与代码状态自洽——这是"呈现层注水"，不是"数据造假"。

最具讽刺性的病灶是标准的选择性适用：项目自家规范要求每个 run 的 notes"三行必填：假设→观察→结论（失败也要记）"[^166^]，而实测 88 个 run notes 中 76 个残留"待填写"模板头[^167^]；连受制度约束的内部账目尚且未达标，完全不受门禁管辖的 README 成为错误数字活到 HEAD 的温床。处方因此是自家的：README 按"三行必填"标准重写——每个数字可溯源、失败同强度入库。

可信度分级的落点是：**P1（第一幕）可信到账目级，P2（第二幕）应读作计划书而非实绩**。而全项目最危险的不是任何已错的数字，而是训测同集这颗未爆的雷：评测 quality 轴的两个主力集登记 `split="test"`，SFT 默认配置与全部 5 份 yaml 均写 `axis: quality`，全部 7 条 dev run 都在评测测试集上训练[^168^]；数据侧隔离机制已建成且有测试守护，消费侧修复闸（p2-05 C5"训练口改 axis: train，照旧即训测同集假分"）至今未勾[^169^]——污染尚未兑现为报告数字，但正式档按现配置点火即兑现。

本章判断受三处证据边界约束，须如实披露。其一，本评估环境中无 Apple MPS 与昇腾 910B 硬件，凡涉硬件的账目（如 910B 内核编译、MPS 回退路径）仅核对仓内账目之间的一致性，未能独立重跑。其二，第一幕头条数字（"296 绿""72 孙任务"）所依赖的权重文件与主语料均不在仓内，无法独立重放，该部分真实性判断的证据级止于 D。其三，两处合规判断——CC BY-NC 语料用于蒸馏、GLM API 服务条款（ToS）——缺乏正式法律分析支撑，判为 D 级；本报告仅陈述证据状态，不判定合规或违规。

### 6.2 分读者建议

**对学习者**：P1 与 runs/ 目录是最有价值的部分：数字链物理自洽的主训练 run、"床前明月光"接出乱文的采样记录[^170^]、编排者把自身假绿升格为 R19 反模式的完整 git 链，都是别处看不到的一手教材；但 README 的每个数字必须对照账目读，核验入口是本报告第 3 章而非门面文字。**对工程团队**：OpenSpec 编排、`_assert_ran_dialect` 防假绿双闸、D11 版权边界四层落点均可直接迁移；同时要带走一条反面教训——CI 只覆盖 scratch/ 而唯一活跃主线 release/ 零门禁[^171^]，使一个重复装饰的 fixture 能活着入库并击穿头条主张，门禁必须跟着主战场走。**对评估者**：不要引用 README 的任何数字（296、72、+31.7pp 都有口径或时效问题），引用应落到 run 档的 metrics.jsonl 与评测报告原文，并优先采用核验表中证据级为 A 的条目。
